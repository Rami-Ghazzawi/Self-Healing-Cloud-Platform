# Monitoring & Observability

## 1. Monitoring Architecture

The platform uses Amazon CloudWatch as the primary monitoring and observability service.

Application health and infrastructure metrics are collected from Amazon ECS and the Application Load Balancer. CloudWatch evaluates these signals and triggers alarms when predefined thresholds are exceeded.

The resulting alarm events are routed through Amazon EventBridge to the Autonomous Self-Healing Controller.

```text
Application
     ↓
ECS / ALB
     ↓
Amazon CloudWatch
     ↓
Metrics + Logs
     ↓
CloudWatch Alarms
     ↓
Amazon EventBridge
     ↓
Self-Healing Controller
```

This architecture separates **observation** from **automated recovery**.

---

## 2. ECS Metrics

The ECS service provides metrics that describe the resource utilization and operational state of the application tasks.

### CPUUtilization

`CPUUtilization` measures the percentage of CPU resources being consumed by the ECS service.

The project uses this metric to detect sustained high CPU utilization.

The CPU alarm is configured with an 80% threshold and requires the condition to persist for two consecutive evaluation periods.

A CPU alarm can trigger the self-healing controller to increase the ECS service desired task count within the configured safety limits.

---

### MemoryUtilization

`MemoryUtilization` measures the percentage of memory resources being consumed by the ECS service.

The platform monitors this metric to identify sustained memory pressure.

When the configured threshold is exceeded, the self-healing controller evaluates the ECS and ALB health state before deciding whether a task should be replaced or the service should scale out.

---

### LiveTaskCount

`LiveTaskCount` provides visibility into the number of currently running ECS tasks.

This metric is useful for verifying that the service maintains the expected number of running tasks and for observing scaling and recovery operations.

It also provides supporting evidence during self-healing tests.

---

## 3. ALB Metrics

The Application Load Balancer provides additional application-level health signals.

### HTTPCode_Target_5XX_Count

`HTTPCode_Target_5XX_Count` measures the number of HTTP 5XX responses generated by the targets behind the load balancer.

The metric is used to detect application-side failures that may not necessarily be visible through CPU or memory utilization.

When a significant number of target 5XX responses is detected, the self-healing controller inspects the health of the ECS tasks and ALB targets before selecting a recovery action.

---

### Target Health

ALB target health provides information about whether ECS tasks are healthy and capable of receiving traffic.

The self-healing controller uses target health as an additional signal when evaluating failures.

This prevents the system from blindly restarting healthy tasks when a 5XX alarm occurs.

---

## 4. CloudWatch Alarms

CloudWatch alarms convert monitoring signals into actionable events.

### CPU Alarm

The ECS CPU alarm monitors:

```text
Metric: CPUUtilization
Threshold: 80%
Evaluation: 2 periods
Period: 60 seconds
Statistic: Average
```

The alarm transitions to `ALARM` when CPU utilization remains above the configured threshold for the required evaluation periods.

This event can initiate the CPU self-healing workflow.

---

### Memory Alarm

The ECS memory alarm monitors:

```text
Metric: MemoryUtilization
Threshold: 80%
Evaluation: 2 periods
Period: 60 seconds
Statistic: Average
```

The alarm provides the trigger for the memory self-healing workflow.

The controller subsequently examines task and target health before performing a recovery action.

---

### ALB 5XX Alarm

The ALB alarm monitors:

```text
Metric: HTTPCode_Target_5XX_Count
Statistic: Sum
Period: 60 seconds
Evaluation: 1 period
Threshold: 10
```

The alarm is designed to detect significant application failures reported through the load balancer.

The self-healing controller does not automatically restart tasks solely because the alarm fired. It first evaluates the target health and ECS task state to determine the appropriate response.

---

## 5. Logs

CloudWatch Logs provides centralized logs for both the application and the self-healing controller.

### Self-Healing Lambda

```text
/aws/lambda/dev-self-healing-controller
```

The Lambda logs controller decisions, recovery actions, verification results, retry information, and escalation events.

One important recovery state is:

```text
RECOVERY_CONFIRMED
```

This indicates that the verification phase detected that the monitored alarm had returned to a healthy state.

---

### ECS Application

```text
/ecs/dev-app
```

The ECS application logs are used to investigate application behavior, errors, and runtime events.

Combining application logs with ECS and ALB metrics provides a more complete view of the system's operational state.

---

## 6. Alarm State Lifecycle

The normal lifecycle of a monitored condition is:

```text
OK
 ↓
ALARM
 ↓
Recovery Action
 ↓
Verification
 ↓
OK
```

For example, during the CPU self-healing test:

```text
Normal CPU
    ↓
CPU Stress
    ↓
CPUUtilization > 80%
    ↓
CloudWatch Alarm = ALARM
    ↓
EventBridge
    ↓
Self-Healing Lambda
    ↓
ECS Recovery Action
    ↓
Verification
    ↓
CloudWatch Alarm = OK
    ↓
RECOVERY_CONFIRMED
```

If the condition remains unresolved, the self-healing controller can enter its retry workflow instead of immediately declaring recovery.

---

## 7. Monitoring vs Self-Healing

Monitoring and self-healing have different responsibilities.

### Monitoring

**Monitoring detects the problem.**

CloudWatch collects metrics and logs, evaluates thresholds, and changes alarm states when abnormal conditions are detected.

```text
Metrics
  ↓
CloudWatch
  ↓
Alarm
```

### Self-Healing

**Self-Healing responds to the problem.**

EventBridge routes the alarm event to the Self-Healing Controller, which evaluates the system state and performs a bounded recovery action.

```text
Alarm
  ↓
EventBridge
  ↓
Self-Healing Controller
  ↓
Inspect
  ↓
Decide
  ↓
Recover
  ↓
Verify
```

This separation is an important design principle of the platform: **CloudWatch observes the system, while the Self-Healing Controller acts on the observed failure.**
